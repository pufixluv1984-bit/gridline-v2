# Архитектура

## Схема

```
Браузер (Vite + React, GitHub Pages)
   │  только публичный ключ, вход через Supabase Auth
   ▼
Supabase: Postgres + RLS  ◄── Edge Function "sync-f1" (по расписанию, pg_cron + pg_net)
   │                              │
   │ SQL-функции подсчёта очков    └── Jolpica F1 API / OpenF1 (только отсюда)
   ▼
score_lines → рейтинги, разбор этапа
```

Браузер читает и пишет только свою Supabase-базу. Во внешние F1-API он не ходит никогда: данные общие для всех, их один раз кладёт серверная функция.

## Фронтенд

- Vite + React 19 + TypeScript strict. `HashRouter` (на GitHub Pages прямые ссылки без хэша дают 404). В `vite.config.ts` `base` равен имени репозитория.
- Структура: `src/app` (роутер, провайдеры), `src/features/{auth,leagues,predict,fantasy,schedule,results,profile}`, `src/ui` (кнопки, карточки, таблицы, графики, подсказки), `src/lib` (supabase-клиент, время, типы базы), `src/styles` (токены).
- Данные: TanStack Query. Запросы только через модуль `src/lib/api/*`, вызывать Supabase из компонентов напрямую нельзя.
- Время: единый хук `useServerNow()` (раз в минуту сверяется с RPC `server_now()`, между сверками тикает локально). Все таймеры и «закрыто/открыто» берут время отсюда.
- Графики — свои SVG-компоненты (варианты в экране «Варианты графика»). Перетаскивания нет, выбор кликами.
- Каждый экран из макета = страница + состояния: загрузка, пусто, ошибка, сеть. Экраны состояний есть в макетах (Empty-States, Error-*).

## База: таблицы (черновик, уточнить в фазе 1)

| Таблица | Содержимое |
|---|---|
| `profiles` | id = auth.users.id, ник, цвет аватара, `avatar_path` (фото в Storage `avatars/<id>/<stamp>-256/-512`, миграция 0020), `avatar_text` (свои буквы), `in_global_ranking` (по умолчанию false) |
| `leagues`, `league_members` | лига, инвайт-код (6 символов), лимит игроков, `bonus_config jsonb`; роли `owner`/`member` |
| `seasons`, `events`, `sessions` | сезон, уик-энд (`is_sprint`), сессии со стартом в UTC и `deadline_at` |
| `drivers`, `constructors`, `season_entries` | пилоты и команды по сезонам, номера, цвета |
| `predictions` | один на (user, event): блоки qualy / race / bonus, бустер (`boost_block`) |
| `results` | фактические результаты сессий, `is_final`, источник (`api`/`manual`) |
| `score_lines` | строка начисления: user, event, блок, причина, очки, `provisional`; уникальный ключ для идемпотентности |
| `fantasy_squads`, `fantasy_picks`, `fantasy_transfers`, `fantasy_chips`, `fantasy_prices`, `fantasy_scores` | состав на этап, трансферы, чипы, цены по этапам, очки |
| `notifications` | уведомления лиге (перенос сессии и т.п.) |

Типы TypeScript генерируются из базы (`supabase gen types`), руками не пишутся.

## Безопасность (обязательные правила)

1. RLS включён на **каждой** таблице схемы `public`; таблица без политик недоступна. Тест, который падает, если нашлась таблица без RLS.
2. `predictions`:
   - insert/update: `user_id = auth.uid()` и `now() < deadline_at` соответствующей сессии (проверка в `with check`, плюс триггер как второй рубеж);
   - select: свой всегда; чужой — только если `now() >= deadline_at` **и** есть общая лига. Общую лигу проверять security-definer функцией `shares_league(uid)` (чтобы не получить рекурсию политик).
3. `results`, `score_lines`, `events`, `sessions`, `drivers`: клиент только читает. Пишет Edge Function с `service_role` и SQL-функции.
4. Ручной ввод результата: RPC `owner_set_result(...)`, внутри проверка, что вызывающий — владелец лиги. Результат ручного ввода хранится с источником `manual`.
5. Подсчёт очков (`recompute_event_scores(event_id)`): `security definer`, закрыт для вызова из клиента, идемпотентен (пересоздаёт строки этапа в одной транзакции). Тест: двойной запуск даёт те же очки.
6. Бустер: ограничение «один на каждые 5 этапов» проверяется базой, не интерфейсом.
7. Инвайт-код: вступить можно только через RPC `join_league(code)` с ограничением частоты; перебор кодов не должен быть выгоден (6 символов + лимит попыток).
8. Фронт: нет `service_role`, нет `dangerouslySetInnerHTML` с пользовательским текстом, ник и название лиги ограничены по длине и символам на уровне базы (`check`).
9. Auth: только OAuth (Google, Discord), провайдер Email в Supabase выключен; редирект-URL только для адреса сайта и localhost.
10. Бэкапы: на бесплатном плане Supabase их нет. Ночная выгрузка `pg_dump` через GitHub Actions (строка подключения в секретах), хранить артефакты 14 дней.
11. Проект на бесплатном тарифе ставится на паузу после недели без активности: раз в 2–3 дня GitHub Actions делает лёгкий запрос к базе.
12. Фото профиля (миграция 0020): корзина Storage `avatars`, публичное чтение по неугадываемому пути, запись и удаление только в своей папке `<uid>/`, только WebP/JPEG до 512 КБ (SVG нельзя). Браузер проверяет тип по первым байтам, кадрирует и сжимает до 256 и 512 px. Фото в ответы экранов дописывает `avatars_fill` с правами игрока (чужое фото видно только при общей лиге). Экраны с игроками — обёртки над `<name>_plain`: **логику экрана меняй в `<name>_plain`**, иначе пропадут фото.

## Поток данных F1

- Edge Function `sync-f1`: (а) раз в сутки обновляет расписание и `deadline_at`; (б) после конца сессии каждые 5–10 минут опрашивает источник, пока нет результата; (в) 48 часов после гонки раз в час перепроверяет результат (штрафы) и помечает очки `provisional`, затем фиксирует.
- Вызов по расписанию: `pg_cron` + `pg_net` внутри Supabase.
- Запись результата → триггер/вызов `recompute_event_scores`. Лимиты внешних API: уточнить по их документации и кэшировать всё в базе.
- Сбой источника → владелец лиги вводит результат вручную (тот же код подсчёта).

## Тесты

- pgTAP: RLS (чужой прогноз до/после дедлайна; запись после дедлайна отклонена; участник не может вызвать owner-RPC; таблицы без RLS), подсчёт (каждая строка таблицы очков, бустер, первый сход с ничьёй по кругам и «Никто», идемпотентность, тай-брейк).
- Vitest: форматирование времени/поясов, хук таймера, чистая UI-логика.
- Проверка экранов вручную на 1440 и 2K, скриншоты в описании фазы.

## Скорость и отзывчивость

Сам React для такого объёма (таблицы до 30 строк, 22 пилота, пара графиков) не узкое место. Лаги дают другие вещи, поэтому они заложены в проект с самого начала.

| Риск | Что делаем |
|---|---|
| Тяжёлые эффекты (`blur` в анимации появления, большие `box-shadow`, `zoom 1.4` на 2K) | Анимируем только `transform` и `opacity`; свечения статичные; `will-change` только на живых элементах; уважаем `prefers-reduced-motion` |
| Экран «Трассы» в макете весит около 437 КБ | Каждая трасса отдельный SVG-файл, подгрузка при открытии; без инлайна всех трасс в бандл |
| Фото пилотов и машин | WebP/AVIF, размеры под карточки (не больше 2× от показа), `loading="lazy"`, заданные `width`/`height` против прыжков вёрстки |
| Шрифты | Свои файлы, `woff2`, подмножество латиница+кириллица, `font-display: swap`, `preload` для основного |
| Размер JS | `React.lazy` по маршрутам; фэнтези и графики грузятся только на своих экранах; проверять размер сборки в CI |
| Запросы к базе | Один запрос на экран через вью или RPC; индексы на внешние ключи и `(event_id, user_id)`; кэш TanStack Query, `staleTime` для расписания и результатов, префетч соседних экранов |
| Отклик на нажатия | Оптимистичные обновления для прогноза и состава; откат с сообщением при отказе базы |
| Задержка сети | Проект Supabase в Европе (Франкфурт) |
| Таймеры | Один общий тикер на всё приложение, а не `setInterval` в каждом компоненте |

Проверка: Lighthouse на десктопе (производительность не ниже 90), ручная проверка на 1440 и 2K, профиль в DevTools на экранах с анимациями.

## CI/CD (GitHub Actions)

- На каждый push: install, typecheck, lint, test, build.
- На `main`: деплой на Pages (секреты `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`).
- Cron: keep-alive (пинг базы), ночной бэкап.
- Миграции на боевую базу применять осознанно (`supabase db push`) из локальной машины или отдельного ручного workflow, не автоматически на каждый push.
